# Releasing

The action runs directly from the repository at the selected Git ref; there is no separate build artifact. The existing `v1` release and tag predate the current cleanup fixes. Until a new compatible release is published and `v1` is updated, the README examples use a reviewed commit SHA.

A maintainer with release and tag permissions performs the following steps after the release changes have been reviewed and merged. Use a new semantic version for each release, preserve published version tags, and use a new major version for breaking changes. Never move the major tag to an unreviewed commit.

1. Select the exact reviewed commit on `master`, confirm that all required checks pass, and review the changes since the previous release. Run `python -m unittest discover -s tests` on that commit. Run the action in a Linux GitHub Actions workflow with working WireGuard and SSH endpoints; exercise success and failure cleanup and confirm the runner's original `net.ipv4.ip_forward` value is restored.
2. Inspect the release contents from that exact commit, including `action.yml` and the forwarding cleanup tests. For example, extract `git archive <commit>` into a temporary directory and run the unit tests there. Confirm that `Cleanup` runs on failure and restores the saved forwarding value, and that the archived action matches the reviewed commit. Do not release if verification fails.
3. Create a new release-specific tag such as `v1.0.1` at the verified commit and publish a GitHub release for that tag with notes describing the changes. Confirm the published tag resolves to that same commit and inspect its `action.yml`. Do not reuse or move a release-specific tag.
4. Update the compatible major tag `v1` to the same commit only after the release is verified. Check the existing remote tag first and use a lease to avoid overwriting a concurrent update. Verify the remote `v1` and release-specific tag both resolve to the verified commit. If a tag protection rule or immutable release prevents moving `v1`, stop and resolve that policy with repository maintainers; do not bypass it. The existing `v1` tag is associated with a GitHub release, so verify that repository settings permit the update before attempting it.
5. Update both README files through review to describe the new release and the chosen examples. Users pinned to a commit must update their workflows themselves; major-tag users receive future compatible updates when the tag moves.

See GitHub's [action release guidance](https://docs.github.com/en/actions/how-tos/create-and-publish-actions/manage-custom-actions) and [immutable release guidance](https://docs.github.com/en/actions/how-tos/create-and-publish-actions/using-immutable-releases-and-tags-to-manage-your-actions-releases).
